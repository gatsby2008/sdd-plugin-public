# plan — Reference

Reference material for `/sdd:plan`. Templates and tables that are read on-demand during execution. `SKILL.md` is the execution flow; this file holds the artifact structures and output formats.

---

## Tag conventions

Used in the Change column of the plan's `## Target Files` table:

- `[infra]` — cross-cutting infrastructure (exception handlers, filters, advice classes)
- `[mock-consumer]` — test file whose mocks may need updating due to a target class's signature change
- `[reference-update]` — file containing a string reference to a renamed or removed endpoint, path, constant, or method
- `[⚠ risk:<signal>]` — high-risk file detected by Step 6 (e.g. `[⚠ risk:db-migration]`, `[⚠ risk:auth-security]`)
- (no tag) — primary target derived from spec's Implementation Context or cache

The Existing test file detection guard does not add a tag — it adjusts the path of test rows in place so they point at the real file using the project's naming convention.

`/sdd:implement` reads the file paths; tags are advisory annotations for human reviewers and for `/sdd:handoff` to surface in the execution pack.

---

## Risk signals — Interpreting

Used in Step 6 to translate detected signals into Approach annotations:

| Signal | Meaning | Why it's high risk |
|---|---|---|
| `db-migration` | Schema-changing Flyway/Liquibase files or spec mentions table/column DDL | Irreversible in production; failed migrations can block deploys |
| `auth-security` | Security config, filters, JWT/OAuth code | Bugs leak data or lock out users; hard to roll back safely |
| `breaking-api` | Spec announces a contract change | Consumers break silently until they're updated |
| `data-destructive` | Spec mentions deletes/purges/truncate on production data | Data loss is unrecoverable |
| `concurrency` | Transactional boundaries, locks, distributed transactions | Race conditions are intermittent and hard to test |

## Plan file template

Used in Step 7 to write `.specwork/_plan/<slug>-plan.md`:

```markdown
# <slug> — Implementation Plan

> Generated by `/sdd:plan`
> The plan is **living**: `/sdd:implement` may append target files or steps if drift is detected during implementation.

## Target Files

| File | Change |
|------|--------|
| `src/main/.../Foo.java` | <one-line description of what changes> |
| `src/intTest/.../FooIT.java` | <one-line description — path matches the project's existing test convention> |
| `src/.../RestExceptionHandler.java` | [infra] <handler change derived from HTTP status code in spec> |
| `src/test/.../OtherServiceTest.java` | [mock-consumer] Update mocks of Foo to match new signature |
| `src/main/.../RetryNotificationService.java` | [reference-update] Update log string referencing removed legacy endpoint |
| `src/main/.../db/migration/V42__add_consent.sql` | [⚠ risk:db-migration] Add consent_status column |

Heuristic-discovered rows carry a tag prefix (`[infra]`, `[mock-consumer]`, `[reference-update]`, `[⚠ risk:<signal>]`) in the Change column. Primary rows have no tag.

## Approach

Ordered steps in plain language — what changes in what order and why. Prefix high-risk steps with `⚠ HIGH RISK (<signal>)` — see *Risk Assessment* in the template below.

1. <step>
2. ⚠ HIGH RISK (db-migration) <step that touches schema>
3. <step>

## Out-of-Plan Files

Files explicitly excluded from this implementation (from spec's `## Out of scope` or `## Expected Change Scope > Avoid touching`):

- `<path or pattern>`

## Open Questions

Planning-level ambiguities that must be resolved before `/sdd:implement` can run. **Not** business behavior questions (those belong in the spec). Use checkboxes with `#N` identifiers — same convention as the spec.

- [ ] **#1** <discovery-level question, e.g. "Two candidate classes match the spec hint — `OrderController` and `OrderQueryController`. Which is the target?">
- [x] **#2** <resolved planning question> — resolved: <answer>

If the plan has no unresolved planning ambiguities, write the section header followed by `_None._` so the gate has something to read.

## Risk Assessment

Emit this section **only when** Step 6 detected at least one signal. Omit entirely otherwise.

Recommended workflow for the high-risk steps below:
- Commit each risky step in isolation — do not bundle with low-risk changes
- Run the project's test suite locally after each high-risk step (not only at `/sdd:mr`)
- Request extra peer review on the MR; flag the risky steps in the description

Signals detected:
- **db-migration** — spec: "alter table", "schema change" · files: `src/.../V42__add_consent.sql`
- **auth-security** — files: `src/.../JwtFilter.java`

Affected Approach steps:
- Step 2 — `db-migration`
- Step 5 — `auth-security`

## Risks / Constraints

Free-form notes — rule conflicts, soft warnings, or risky areas the structured signals above didn't capture.

- <note>
```

## Step 6 summary template

Used in Step 6 (the final step) to print the post-plan summary:

```text
Plan created.

Plan:
  .specwork/_plan/<slug>-plan.md

Target files:           <N> total
  Primary:              <P>
  [infra]:              <I>
  [mock-consumer]:      <M>
  [reference-update]:   <U>
  [⚠ risk]:             <R>
Cache updated:          <C> new entries
Plan Open Questions:    <K unresolved> / <total>

Heuristic additions:
  [infra]             src/.../RestExceptionHandler.java
                      (HTTP 404 detected in spec → handler proposed)
  [mock-consumer]     src/test/.../PaymentHandlerTest.java
                      (mocks OrderService → may need signature update)
  [reference-update]  src/.../RetryNotificationService.java
                      (log references removed legacy endpoint)

Test path resolution:
  OrderController → src/intTest/.../OrderControllerIT.java (existing)
  (skipped duplicate proposal of OrderControllerTest.java)

Spec consistency:
  idempotent + per-call side effect → added plan OQ #3

⚠ HIGH RISK detected:
  db-migration   Step 2 — adds column to consent table
  auth-security  Step 5 — edits JwtFilter

  Recommended: commit risky steps in isolation, run tests locally after each.

Next:
  Review the plan, then run /sdd:implement.
  (If there are unresolved Plan Open Questions, resolve them in the plan first — /sdd:implement will block.)
```

The conditional-print rules for each block (when to omit, when to print) live in `SKILL.md` Step 6.
