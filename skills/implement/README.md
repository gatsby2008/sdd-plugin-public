# Implement

Implements the next focused change from the spec using bounded context and minimal
diffs. Reads the spec, rules, and implementation cache — then applies the change,
runs targeted tests, and recommends the next pipeline phase.

One step per invocation. Changes accumulate in the working tree without commits
between steps — run `/sdd:implement` multiple times, then `/sdd:commit` once when done.

---

## Prerequisites

- Spec generated by `/sdd:start` exists at `.specwork/_spec/<slug>-spec.md`
- No unresolved Open Questions in the **spec**
- If `/sdd:plan` was run: no unresolved Open Questions in the **plan** either (`.specwork/_plan/<slug>-plan.md`)

`/sdd:implement` Step 3 checks both files via `gates.py check-oqs`. A single unresolved `- [ ]` in either blocks the run. Step 3.5 also validates plan freshness via `gates.py check-staleness`.

If the spec is missing (not yet drafted, or deleted), `/sdd:implement` must stop and require `/sdd:spec` to draft it from the source captured by `/sdd:start`.

---

## Usage

```bash
/sdd:implement
```

---

## What It Produces

Code changes in the source tree plus a completion summary with a complexity
assessment and recommended next phase.

Non-trivial change:

```
Implementation completed.
Complexity assessment:
- async/event-driven changes detected
- multiple layers modified
- non-trivial side effects identified

Recommended next phase:
/sdd:test-design
```

Isolated change:

```
Implementation completed.
Change scope appears isolated and low-risk.

Recommended next phase:
/sdd:commit
```

---

## Typical Session

```bash
/sdd:implement   # implements a focused step, runs targeted tests
/sdd:implement   # implements next step
/sdd:commit      # one commit for all accumulated changes
```

When the complexity assessment recommends `/sdd:test-design`:

```bash
/sdd:implement   # → recommends /sdd:test-design
/sdd:test-design # designs test cases
/sdd:test-impl   # implements them
/sdd:commit
```

## Implementation Cache

`/sdd:implement` reads `.specwork/_state/<slug>-implementation-cache.json` at startup
to avoid redundant discovery:

```json
{
  "repositories": ["LeadsRepository"],
  "related_tests": ["LeadsServiceTest"],
  "similar_classes": ["LeadsProcessor"],
  "patterns": ["fallback lookup uses person + collateral identity"],
  "notes": ["leadId lookup is exercised in IT only"]
}
```

**How it helps:**
- Skips broad `find` scans for known repositories
- Avoids `grep -r` when test files are pre-identified
- Reduces token consumption by ~15–40% across repeated steps

The cache is **append-only** and updated automatically at the end of each run via `gates.py merge-cache`.

## Troubleshooting

**"Missing spec"**
`/sdd:implement` must stop here. It cannot continue without the canonical `.specwork/_spec/<slug>-spec.md` generated by `/sdd:start`. Regenerate it with `/sdd:start`, then rerun `/sdd:implement`.

**"Unresolved Open Questions"**
Resolve all `- [ ]` items in the `## Open Questions` section. The skill checks both files (when a plan exists):
- Spec: `.specwork/_spec/<slug>-spec.md` — business behavior ambiguity
- Plan: `.specwork/_plan/<slug>-plan.md` — discovery/implementation-path ambiguity

**Ambiguity discovered mid-implementation**
The skill stops, appends the question to the spec as `- [ ] <question>`, and
asks you to answer it there before rerunning. Open the spec, answer inline, mark
it `- [x]`, then rerun `/sdd:implement`. The spec is the persistent record — answers
left only in the conversation are lost between sessions.

**Test failure — escalation triggered**
The skill stops, reports the failing area and fixes attempted, and leaves the
working tree as-is for manual review. Fix the issue, then rerun `/sdd:implement`.

## Pipeline Position

```
/sdd:start
/sdd:implement     ←  you are here (repeat per step)
  ↓ low complexity          ↓ high complexity
/sdd:commit             /sdd:test-design
                       /sdd:test-impl
                       /sdd:commit
/sdd:code-review
/sdd:mr
/sdd:mr-address
/sdd:close
```
